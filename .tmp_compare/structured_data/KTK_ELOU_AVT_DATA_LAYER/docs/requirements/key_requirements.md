**Ключевые ФТТ и НФТ КТК ЭЛОУ-АВТ**

Архитектура · Инфраструктура · ИИ-модуль · Информационная безопасность · Техническое решение

# 1. Архитектура

| **Код**        | **Тип** | **Ключевое требование / образ результата**                                                                                                                                                                             |
|----------------|---------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **АРХ-ФТТ-01** | **ФТТ** | Решение должно быть построено как модульный набор независимо развёртываемых сервисов с закреплёнными владельцами данных, версионированными API-контрактами и запретом прямого доступа к данным другого сервиса.        |
| **АРХ-ФТТ-02** | **ФТТ** | Целевая архитектура должна включать frontend, API Gateway, IdP, сервисы симуляций, сценариев, обучения, совместных сессий, оценивания, отчётности, базы знаний, адаптивных назначений, аудита и отключаемый AI-сервис. |
| **АРХ-ФТТ-03** | **ФТТ** | Единственной прикладной точкой входа должен быть защищённый контур балансировщика нагрузки, WAF и Ingress/API Gateway, маршрутизирующий трафик только к разрешённым сервисам.                                          |
| **АРХ-ФТТ-04** | **ФТТ** | Аутентификация и управление доступом должны выполняться через корпоративный IdP с OAuth 2.0/OIDC, единым входом и централизованной ролевой моделью.                                                                    |
| **АРХ-ФТТ-05** | **ФТТ** | Сервис симуляций должен быть единственным владельцем расчётного состояния, обеспечивать воспроизводимость по версии модели и seed и не иметь управляющего подключения к реальной АСУ ТП.                               |
| **АРХ-ФТТ-06** | **ФТТ** | Система должна поддерживать изолированные одиночные и совместные сессии для оператора, специалиста КИПиА, начальника смены и инструктора с серверной проверкой полномочий каждой команды.                              |
| **АРХ-ФТТ-07** | **ФТТ** | Надёжная доставка команд и межсервисных событий должна обеспечиваться очередью сообщений; синхронизация интерфейсов участников — защищённым WebSocket с восстановлением пропущенных событий.                           |
| **АРХ-ФТТ-08** | **ФТТ** | Постоянные данные должны храниться в PostgreSQL HA, оперативное состояние и сессии — в Redis, документы и учебные материалы — в корпоративном S3-хранилище.                                                            |
| **АРХ-ФТТ-09** | **ФТТ** | TEST, PREPROD и PROD должны быть логически и сетево изолированы и использовать отдельные базы данных, очереди, Redis, S3-бакеты, секреты и сервисные учётные записи.                                                   |
| **АРХ-ФТТ-10** | **ФТТ** | Завершённая тренировка должна формировать неизменяемый пакет доказательств: версии модели и сценария, исходные условия, временную шкалу, действия участников, параметры процесса, тревоги, оценку и контрольные суммы. |
| **АРХ-НФТ-01** | **НФТ** | Базовая конфигурация должна поддерживать не менее 100 одновременно подключённых пользователей и 30 параллельных симуляций с масштабированием до 300 пользователей и 100 симуляций без изменения доменной архитектуры.  |
| **АРХ-НФТ-02** | **НФТ** | Задержка подтверждения команды симулятором должна составлять p95 не более 250 мс, распространения события участникам — p95 не более 500 мс, стандартного API — p95 не более 500 мс.                                    |
| **АРХ-НФТ-03** | **НФТ** | Доступность пользовательского контура PROD должна быть не ниже 99,9% в согласованное учебное окно; критические компоненты не должны иметь единой точки отказа.                                                         |
| **АРХ-НФТ-04** | **НФТ** | Для результатов и аудита должны обеспечиваться RPO не более 15 минут и RTO критического пользовательского контура не более 60 минут; опубликованные версии моделей и сценариев не должны теряться.                     |
| **АРХ-НФТ-05** | **НФТ** | Отказ AI-модуля, LMS, BI, базы знаний или отчётности не должен останавливать активную симуляцию, детерминированное оценивание и сохранение протокола.                                                                  |

# 2. Инфраструктура

| **Код**        | **Тип** | **Ключевое требование / образ результата**                                                                                                                                                                                                                 |
|----------------|---------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **ИНФ-ФТТ-01** | **ФТТ** | Платформа должна быть развёрнута в частном облаке корпоративного периметра на отказоустойчивом Kubernetes-кластере с отдельными node pool, namespace, квотами и сетевыми политиками для TEST, PREPROD и PROD.                                              |
| **ИНФ-ФТТ-02** | **ФТТ** | Внешний и межсегментный трафик должен проходить через резервированные балансировщики, WAF и Ingress; прямой доступ пользователей к pod, БД, Redis, брокеру сообщений и S3 должен быть запрещён.                                                            |
| **ИНФ-ФТТ-03** | **ФТТ** | Контейнерные образы должны храниться в корпоративном реестре и допускаться к развёртыванию только после проверки уязвимостей, состава, лицензий, SBOM, подписи и происхождения.                                                                            |
| **ИНФ-ФТТ-04** | **ФТТ** | CI/CD должен продвигать один и тот же подписанный digest по цепочке TEST → PREPROD → PROD без пересборки и блокировать выпуск при непрохождении обязательных проверок.                                                                                     |
| **ИНФ-ФТТ-05** | **ФТТ** | PREPROD должен воспроизводить топологию, версии платформы, политики безопасности и интеграции PROD в масштабе, достаточном для функциональных, интеграционных, нагрузочных, регрессионных и ИБ-испытаний.                                                  |
| **ИНФ-ФТТ-06** | **ФТТ** | Доступ к PREPROD должен предоставляться только разработчикам и профильным администраторам приложения, Kubernetes-платформы, БД, IdP, сети, ИБ, мониторинга и резервного копирования; пользовательские роли должны проверяться тестовыми учётными записями. |
| **ИНФ-ФТТ-07** | **ФТТ** | В PROD должны быть заведены раздельные административные роли для приложения, платформы, БД, IdP, сети, ИБ, мониторинга и резервного копирования; постоянный интерактивный доступ разработчиков должен быть запрещён.                                       |
| **ИНФ-ФТТ-08** | **ФТТ** | PostgreSQL должен работать в режиме высокой доступности с основным и резервным экземплярами в разных зонах, автоматическим переключением, отдельной БД для каждой среды и восстановлением на заданный момент времени.                                      |
| **ИНФ-ФТТ-09** | **ФТТ** | Redis, очередь RabbitMQ/Kafka и S3-хранилище должны быть развёрнуты отказоустойчиво, иметь раздельные контуры по средам и обеспечивать сохранность, повторную доставку и восстановление данных согласно их классу.                                         |
| **ИНФ-ФТТ-10** | **ФТТ** | Платформа должна включать централизованные мониторинг, метрики, логи, трассировку, SIEM, управление секретами, резервное копирование, уведомления и эксплуатационные панели.                                                                               |
| **ИНФ-ФТТ-11** | **ФТТ** | После неудачного внедрения откат должен быть фактически выполнен по утверждённому runbook и подтверждён проверками доступности предыдущей версии, целостности данных, авторизации, запуска симуляции, совместной сессии, отчётности и аудита.              |
| **ИНФ-НФТ-01** | **НФТ** | Критические сервисы PROD должны иметь не менее двух реплик, распределение по узлам и зонам, PodDisruptionBudget и автоматическое восстановление без ручного переключения пользовательского трафика.                                                        |
| **ИНФ-НФТ-02** | **НФТ** | Вся инфраструктура, сетевые политики, роли, конфигурация и мониторинг должны описываться как код, проходить review и воспроизводимо развёртываться без ручной настройки серверов.                                                                          |
| **ИНФ-НФТ-03** | **НФТ** | Резервное восстановление PostgreSQL, S3, конфигурации и секретов должно проверяться не реже одного раза в квартал с фиксацией фактических RPO/RTO и устранением отклонений.                                                                                |
| **ИНФ-НФТ-04** | **НФТ** | Инфраструктура должна поддерживать горизонтальное масштабирование прикладных сервисов и очередей без остановки активных тренировок и без изменения клиентских настроек.                                                                                    |
| **ИНФ-НФТ-05** | **НФТ** | Критические обновления безопасности инфраструктурного ПО должны устанавливаться в регламентированный срок после проверки в TEST и PREPROD; неподдерживаемые версии компонентов в PROD запрещаются.                                                         |

# 3. ИИ-модуль

| **Код**       | **Тип** | **Ключевое требование / образ результата**                                                                                                                                                                                |
|---------------|---------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **AI-ФТТ-01** | **ФТТ** | AI-модуль должен быть отключаемым на уровне организации, среды, учебной программы и отдельного пользователя; при отключении весь основной функционал тренажёра должен сохраняться.                                        |
| **AI-ФТТ-02** | **ФТТ** | Модель должна запускаться локально на выделенных корпоративных GPU-серверах внутри периметра; передача запросов, журналов, документов или результатов во внешние AI-сервисы запрещается.                                  |
| **AI-ФТТ-03** | **ФТТ** | AI-модуль должен анализировать только завершённые или разрешённые промежуточные результаты и не должен управлять симулятором, изменять технологические параметры, итоговый детерминированный балл или права пользователя. |
| **AI-ФТТ-04** | **ФТТ** | Модуль должен формировать персонализированный разбор действий, выявлять повторяющиеся ошибки, сравнивать траекторию с утверждённым эталоном и предлагать следующие мини-тренировки.                                       |
| **AI-ФТТ-05** | **ФТТ** | Каждая рекомендация должна содержать основание: связанные действия и параметры сессии, применённое правило или фрагмент утверждённой базы знаний, уровень уверенности и явное указание ограничений.                       |
| **AI-ФТТ-06** | **ФТТ** | Ответы должны формироваться только на основании разрешённого контекста пользователя и утверждённых материалов базы знаний с обязательными ссылками на использованные внутренние источники.                                |
| **AI-ФТТ-07** | **ФТТ** | Инструктор или методолог должен иметь возможность просмотреть, отклонить, исправить и скрыть AI-рекомендацию; все изменения и итоговая публикация должны фиксироваться в аудите.                                          |
| **AI-ФТТ-08** | **ФТТ** | Версии модели, системных инструкций, шаблонов, базы знаний, параметров генерации и фильтров должны сохраняться вместе с результатом анализа и быть воспроизводимыми.                                                      |
| **AI-ФТТ-09** | **ФТТ** | AI-задачи должны выполняться асинхронно через отдельную очередь и пул ресурсов, чтобы не влиять на расчётный такт симулятора, API и совместные сессии.                                                                    |
| **AI-НФТ-01** | **НФТ** | На утверждённом контрольном наборе доля фактически корректных утверждений должна быть не ниже 95%, доля ответов с полной ссылочной прослеживаемостью — 100%, критические противоречия требованиям безопасности — 0.       |
| **AI-НФТ-02** | **НФТ** | Персональный разбор одной завершённой сессии должен формироваться не более чем за 30 секунд для p95 при референсной нагрузке либо переводиться в фоновую задачу с отображением статуса.                                   |
| **AI-НФТ-03** | **НФТ** | Модуль должен быть защищён от prompt injection, утечки системных инструкций, несанкционированного расширения контекста и извлечения данных другого пользователя или подразделения.                                        |
| **AI-НФТ-04** | **НФТ** | До ввода новой модели или версии в PROD должны выполняться офлайн-оценка, проверка качества на ролевых сценариях, red teaming, ИБ-проверка и контролируемое сравнение с действующей версией.                              |
| **AI-НФТ-05** | **НФТ** | Работа AI-модуля должна наблюдаться по метрикам доступности, задержки, использования GPU, отказов, качества, доли отклонённых рекомендаций и дрейфа без сохранения избыточных персональных данных.                        |

# 4. Информационная безопасность

| **Код**       | **Тип** | **Ключевое требование / образ результата**                                                                                                                                                                                                              |
|---------------|---------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **ИБ-ФТТ-01** | **ФТТ** | Доступ должен предоставляться через корпоративный SSO/IdP по OAuth 2.0/OIDC с многофакторной аутентификацией для привилегированных и удалённых административных операций.                                                                               |
| **ИБ-ФТТ-02** | **ФТТ** | Ролевая модель должна разделять обучаемого-оператора, обучаемого-специалиста КИПиА, начальника смены, инструктора, методолога, аудитора, разработчика и администраторов приложения, платформы, БД, IdP, сети, ИБ, мониторинга и резервного копирования. |
| **ИБ-ФТТ-03** | **ФТТ** | Полномочия должны назначаться по принципам минимально необходимых прав, разделения обязанностей и запрета совмещения конфликтующих ролей; административный доступ в PROD должен быть временным, согласованным и полностью аудируемым.                   |
| **ИБ-ФТТ-04** | **ФТТ** | Авторизация должна проверяться сервером для каждого API-запроса, объекта, экспорта, WebSocket-подключения и события; клиентская проверка прав не должна считаться средством защиты.                                                                     |
| **ИБ-ФТТ-05** | **ФТТ** | Межсервисные соединения должны использовать отдельные сервисные идентичности, mTLS и сетевые политики; доступ к БД, Redis, брокеру и S3 должен разрешаться только требуемым сервисам.                                                                   |
| **ИБ-ФТТ-06** | **ФТТ** | Данные должны шифроваться при передаче и хранении утверждёнными корпоративными средствами; ключи и сертификаты должны управляться централизованно с ротацией и отзывом.                                                                                 |
| **ИБ-ФТТ-07** | **ФТТ** | Пароли, токены, ключи и иные секреты должны храниться только в корпоративной системе управления секретами и не должны присутствовать в коде, образах, логах, CI/CD-переменных открытого вида или клиентском bundle.                                     |
| **ИБ-ФТТ-08** | **ФТТ** | Неизменяемый аудит должен фиксировать входы, выдачу и изменение прав, административные действия, команды симуляции, изменение контента, экспорт, AI-анализ, выпуск и откат с передачей событий в SIEM.                                                  |
| **ИБ-ФТТ-09** | **ФТТ** | Secure SDLC должен включать threat modeling, review кода, SAST, SCA, DAST, secret scanning, проверку IaC и контейнеров, тестирование на проникновение и блокирующие критерии выпуска.                                                                   |
| **ИБ-ФТТ-10** | **ФТТ** | Каждый релизный образ должен иметь SBOM, цифровую подпись, контрольную сумму и подтверждённое происхождение; запуск неподписанного или не прошедшего проверку образа должен блокироваться политикой кластера.                                           |
| **ИБ-ФТТ-11** | **ФТТ** | Загружаемые документы и медиафайлы должны проверяться по типу, размеру, сигнатуре, вредоносному содержимому, уровню доступа и праву публикации до помещения в доступную пользователям базу знаний.                                                      |
| **ИБ-НФТ-01** | **НФТ** | Критические уязвимости должны устраняться или компенсироваться не позднее 24 часов, высокие — 7 календарных дней, средние — 30 календарных дней с документированным контролем исключений.                                                               |
| **ИБ-НФТ-02** | **НФТ** | 100% привилегированных действий и событий доступа к персональным или чувствительным данным должны иметь связанный идентификатор пользователя, роль, время, источник, объект, результат и correlation ID.                                                |
| **ИБ-НФТ-03** | **НФТ** | Журналы безопасности должны передаваться в SIEM не позднее 60 секунд после события, быть защищены от изменения и храниться в срок, установленный корпоративной политикой и классом данных.                                                              |
| **ИБ-НФТ-04** | **НФТ** | Резервные копии должны быть зашифрованы, изолированы от основных административных учётных записей и регулярно проверяться на восстановление без обхода ролевой модели и аудита.                                                                         |
| **ИБ-НФТ-05** | **НФТ** | Перед промышленным запуском и после существенных изменений решение должно проходить независимое тестирование на проникновение без незакрытых критических и высоких уязвимостей.                                                                         |

# 5. Техническое решение: код и frontend

| **Код**        | **Тип** | **Ключевое требование / образ результата**                                                                                                                                                                                                       |
|----------------|---------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **ТЕХ-ФТТ-01** | **ФТТ** | Пользовательский интерфейс должен быть реализован на React и TypeScript в strict-режиме как браузерное приложение/PWA с единой кодовой базой и модульным разделением по бизнес-функциям.                                                         |
